## Кодекс поведения

Участвуя в этом проекте, вы соглашаетесь соблюдать наш [Кодекс поведения](CODE_OF_CONDUCT.ru.md), который описывает ожидания в отношении уважительного и инклюзивного взаимодействия.

## Как я могу помочь?

### Сообщения об ошибках

Если вы столкнулись с ошибкой, пожалуйста:

1. **Просмотрите существующие issue**: проверьте, не сообщал ли кто-то об этой проблеме ранее.
2. **Создайте новый issue**: если ничего не нашлось, создайте новый issue и укажите:
   - понятный заголовок;
   - шаги для воспроизведения ошибки;
   - ожидаемое и фактическое поведение;
   - скриншоты или фрагменты кода, если это уместно.

### Предложение улучшений

Чтобы предложить новые возможности или улучшения:

1. **Просмотрите существующие issue**: убедитесь, что такое предложение ещё не выдвигалось.
2. **Создайте новый issue**: укажите:
   - чёткое описание улучшения;
   - обоснование предложения;
   - любые подходящие примеры или ссылки.

### Отправка pull request

Для вклада в виде кода:

1. **Сделайте форк репозитория**: создайте собственную копию репозитория.
2. **Создайте ветку**: используйте описательное имя (например, `feature/new-model` или `bugfix/issue-123`).
3. **Внесите изменения**: реализуйте изменения понятным и лаконичным кодом.
4. **Напишите тесты**: убедитесь, что новые возможности или исправления покрыты тестами.
5. **Зафиксируйте изменения**: следуйте нашим правилам оформления сообщений коммитов.
6. **Отправьте в свой форк**: загрузите изменения.
7. **Откройте pull request**: дайте подробное описание изменений и сошлитесь на связанные issue.

## Настройка окружения разработки

Чтобы настроить окружение для разработки:

1. **Клонируйте репозиторий**:

   ```bash
   git clone https://github.com/plexe-ai/plexe.git
   cd plexe
   ```

2. **Установите зависимости**:

   ```bash
   pip install poetry
   # Войдите в виртуальное окружение.
   # В современных версиях Poetry используется 'shell', в более старых может потребоваться 'env activate'
   poetry shell
   # ИЛИ: poetry env activate (для старых версий или особых конфигураций)

   # Установите нужные экстра-пакеты (например, AWS, PySpark)
   # Примечание: pyspark и databricks-connect взаимно исключают друг друга
   poetry install -E aws -E pyspark

   # Запустите setup.py, чтобы настроить хуки pre-commit
   python setup.py
   ```

3. **Запустите тесты**:

   ```bash
   # Если 'poetry shell' выше сработал, можно запускать напрямую:
   pytest

   # Если возникает "ModuleNotFoundError", используйте более надёжный вариант:
   poetry run pytest
   ```

4. **Перед открытием PR запустите поэтапные интеграционные тесты**:

   ```bash
   # Требуются ANTHROPIC_API_KEY и локально настроенные Spark/Java
   bash scripts/tests/run_integration_staged.sh
   ```

   Поэтапный набор выполняет три фазы pytest с жёсткими барьерами между ними:
   - `integration_seed`: создаёт переиспользуемые контрольные точки до фазы 3 включительно;
   - `integration_search`: возобновляет работу с контрольных точек и выполняет поиск модели;
   - `integration_eval`: возобновляет работу с контрольных точек поиска, выполняет оценку и проверяет инференс предиктора.

   Набор `tests/integration` — основной интеграционный сценарий перед отправкой PR.
   Docker-цели в Makefile остаются опциональными ручными сквозными проверками.

Перед тем как вносить вклад, убедитесь, что все тесты проходят.

## Переводы

Документация ведётся на английском языке и дублируется на русский в файлах `*.ru.md` рядом с
оригиналами (`CONTRIBUTING.ru.md`, `SECURITY.ru.md` и т. д.). Исключение — README: главная страница
репозитория показывается по-русски, поэтому перевод лежит в `README.md`, а английский оригинал —
в `README.en.md`. Канонична везде английская версия: при расхождении приоритет имеет она.

Каждая пара зарегистрирована в [`docs/translations.json`](docs/translations.json) вместе с хешем
английского оригинала на момент написания перевода:

```bash
python3 scripts/check_translations.py            # показать переводы, оригинал которых изменился
python3 scripts/check_translations.py --update   # зафиксировать текущие коммиты как синхронизированные
```

Если вы меняете английский документ, либо обновите его аналог `*.ru.md` в том же pull request и
заново выполните `--update`, либо оставьте как есть: workflow `Translation Sync` запускается каждый
понедельник, и при расхождении падает, показывая в сводке прогона diff, который осталось перевести.

## Руководства по стилю

### Стандарты кодирования

Следуйте рекомендациям PEP 8 для кода на Python. Основные моменты:

- используйте 4 пробела на уровень отступа;
- ограничивайте длину строк 79 символами;
- используйте осмысленные имена переменных и функций;
- добавляйте docstring ко всем публичным модулям, классам и функциям.

### Сообщения коммитов

Пишите ясные и лаконичные сообщения коммитов:

- **Формат**: `<type>(<scope>): <subject>`
  - **Type** (тип): `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`
  - **Scope** (область): необязательно, например `data`, `model`
  - **Subject** (описание): краткое описание (максимум 50 символов)

- **Пример**:

  ```bash
  feat(model): add support for gemini
  ```
